# 记忆置信度（Confidence）

> 一句话：置信度由**可观测证据**按 Subjective Logic 公式算出，只参与检索排序的 **ε 级微调**，**默认关闭**。
> 它不是排序权重，也不是过滤门槛——实测这两种用法都会让检索变差。

---

## 一、为什么不让人（或模型）直接打分

最初的方案是给每条记忆打一个主观分数（例如 1–5 档）。放弃它有三个理由：

| 问题 | 说明 |
|---|---|
| **不可复现** | 同一个 agent 两次写同一件事，可能给出不同分数；档位边界（3 分和 4 分差在哪）说不清 |
| **粒度不是精度** | 5 档看起来更细，但没有锚点的档位只是 5 个噪声源 |
| **判断应该只发生一次** | 逐条判断 = 每条记忆一次主观决策；把判断压缩成**一次性的证据权重配置**，之后所有记忆用同一把尺子 |

所以这里只做一件事：从 payload 与正文里提取**可观测证据**，按固定公式算分。同一份内容，任何时候算出的分数都相同。

---

## 二、公式（Subjective Logic，Jøsang）

```
b = r / (r + s + W)      belief（相信）
d = s / (r + s + W)      disbelief（不信）
u = W / (r + s + W)      uncertainty（不知道）

b + d + u = 1
```

- `r` / `s`：支持 / 反驳证据的**加权和**
- `W = 2`：non-informative prior 权重

**这个先验的作用**：没有任何证据时 `b = d = 0, u = 1`（完全不确定），而不是 0/0 或 1。
引入本模块前写入的历史节点没有证据记录，正是靠这一条自动落到「未知」——**不需要给它们编一个默认分数**。

| 证据情况 | b | d | u |
|---|---|---|---|
| 无任何证据 | 0 | 0 | **1.0** |
| 1 条 commit 证据（r=1） | 0.33 | 0 | 0.67 |
| 2 条证据（r=2） | 0.50 | 0 | 0.50 |
| 3 支持 + 1 反驳 | 0.50 | 0.17 | 0.33 |

## 三、证据规则（一次性配置）

改动下表等于改所有记忆的分数，请同步更新本节与 `core/confidence.py`。

### 支持证据

| 证据 | 来源 | 权重 | 为什么可信 |
|---|---|---|---|
| `source_path` | payload 带文件路径（`kb_chunk` / `skill_chunk`） | 0.9 | 能指回具体文件 |
| `git_commit` | `type=git_commit` 且带提交信息 | 1.0 | 可回溯到提交 |
| `commit` | 正文含 7–40 位 hex（**至少含一个字母**）或 `PR #N` | 1.0 | 可回溯到提交 / PR |
| `path` | 正文含 Windows / Unix 路径 | 0.8 | 能指回具体文件 |
| `url` | 正文含 http(s) 链接 | 0.8 | 可外部核验 |
| `tested` | 正文含「实测 / 跑出来 / 测试通过 / 复跑 / 验证过 / 全绿 / 断言」 | 0.7 | 声称有实测（抽样精确率 92%） |
| `node` | 正文含 `node N` / `节点 N` | 0.6 | 能指回另一条记忆 |

> **7 位 hex 必须至少含一个字母**：git 短 hash 是 7 位，而纯 7 位数字（如日期 `2026102`）不该被当成提交号。

### 反驳证据

| 证据 | 来源 | 权重 |
|---|---|---|
| `superseded` | `status == "outdated"`（已被明确取代） | 1.0 |
| `hedged` | 正文含**自我指涉**的不确定表达：`待确认 / 待验证 / 存疑 / 未验证 / 无法确认 / 尚无定论 / 不确定是否 / 没有证据 / 缺乏证据 / 暂未核实` | 0.3 |

> ⚠️ **不要**把「可能 / 也许 / 大概 / 或许」加进 hedge 规则。实测这类词在技术文档里绝大多数是在描述**客观可能性**（「未来可能 16G」「状态可能不一致」），拿它当「这条记忆不确定」的信号，精确率只有 **2/12 = 17%**；换成自我指涉的表达后，命中从 438 条降到 62 条，抽样 **8/8 全部正确**。

## 四、映射到排序修正项

```
confidence_norm = clamp((b - CENTER) / SPAN, -1, +1)      # CENTER=0.27, SPAN=0.15
final = cosine + SOFT_RERANK_EPS × (importance_norm + recency_norm)
              + MEMORY_CONFIDENCE_EPS × confidence_norm
```

用**固定线性映射**而不是 z-score，是为了不依赖全库统计量：检索时不必先算一遍均值 / 标准差，同一条记忆在任何库规模下得分一致。

`MEMORY_CONFIDENCE_EPS = 0` 时整项为零，**零开销、行为与改动前完全一致**（有回归测试保证）。

## 五、实测（2026-10-27）

### 5.1 数据与口径

| 项 | 内容 |
|---|---|
| 库规模 | **2969 条**真实记忆（`GET /export?include_payload=true` 全量导出，只读） |
| 评测题集 | **56 题**：exact 22 / semantic 18 / mixed 12 / date 4；multi-gold，共 **449 个 gold 节点**（4 个已不存在于库中） |
| 指标 | Recall@K / MRR@K / nDCG@K，主口径 top-5 |
| 显著性 | bootstrap 2000 次重采样，95% 置信区间 |

> **题集不随本仓库发布**：它是从真实个人记忆反推出来的（query 与 gold 都绑定私人内容），公开会泄露隐私。本节只公开**口径与结果**，复现方式见 5.6。

### 5.2 置信度分布

| 指标 | 全库 2969 条 | gold 449 条 |
|---|---|---|
| 均值 b | 0.276 | **0.404**（+46%） |
| 中位 b | 0.310 | — |
| 最大 b | 0.706 | 0.706 |
| b = 0 占比 | 27.7%（823 条） | — |

按类型（有文件指针的明显更高）：

| type | n | mean b |
|---|---|---|
| `skill_chunk` | 45 | 0.413 |
| `kb_chunk` | 938 | 0.388 |
| `task` | 158 | 0.357 |
| `git_commit` | 23 | 0.333 |
| `novel_chunk` | 124 | 0.310 |

| `record` | 688 | 0.260 |

**gold 节点的置信度系统性高于全库 46%** —— 分数确实在区分「好节点」。

### 5.3 A/B：检索质量

| 方案 | Recall@5 | MRR@5 | nDCG@5 |
|---|---|---|---|
| 基线（无 confidence） | 0.2268 | 0.2298 | 0.2099 |
| **ε=0.05 重排** | **0.2377** (+1.09) | **0.2655** (+3.57) | **0.2482** (+3.83) |
| 硬门槛 `b ≥ 0.2` | 0.1787 (**−4.81**) | 0.2262 (−0.36) | 0.2017 (−0.81) |

括号内为相对基线的百分点变化。

**硬门槛必须否决**：gold 节点里有相当比例 `b = 0`（无任何证据），按 `b` 过滤会把正确答案一起删掉，召回直接掉 4.81 个百分点。

### 5.4 显著性

| 指标 | 提升 | 95% CI | 判定 |
|---|---|---|---|
| Recall@5 | +1.09pp | [−2.48, +5.56] | 不显著 |
| **MRR@5** | **+3.57pp** | **[+0.12, +7.74]** | **显著** |
| **nDCG@5** | **+3.83pp** | **[+0.76, +7.51]** | **显著** |

56 题里 7 题发生变化（赢 5 / 输 2）。

### 5.5 提升来自哪类题

| 题型 | n | ΔMRR@5 | 说明 |
|---|---|---|---|
| **semantic** | 18 | **+13.15pp**（0.3796 → 0.5111，**+34.6%**） | 全部提升来自这里 |
| exact | 22 | 0.00 | FTS 精确匹配，confidence 不参与 |
| date | 4 | 0.00 | 同上 |
| mixed | 12 | ≈0 | 基本持平 |

**confidence 起作用的场景 = 语义题里「几个候选分相近」的时候**——这正是 ε 级 tie-break 的定位。

### 5.6 消融与反例（调了反而更差的三件事）

| 改动 | 结果 | 结论 |
|---|---|---|
| 去掉 `hedged` 规则 | MRR 0.2655 → 0.2595（−0.60pp） | hedge 有用，不能删 |
| `tested` 权重 0.7 → 0.9 | MRR 0.2655 → 0.2565（−0.90pp） | 保持 0.7 |
| 硬门槛 `b ≥ 0.2` | Recall −4.81pp | 否决 |
| ε ≥ 0.1 | MRR 从 0.2655 掉到 0.2149 | 只做微调，不能主导排序 |

### 5.7 稳健性

**k 敏感性**（换 k 值提升是否还在）：

| k | 基线 MRR | ε=0.05 MRR | Δ |
|---|---|---|---|
| 3 | 0.2262 | 0.2619 | +3.57pp |
| 5 | 0.2298 | 0.2655 | +3.57pp |
| 10 | 0.2385 | 0.2717 | +3.32pp |

三个 k 值几乎一致 → 不是评测口径的偶然。

**复现方式**：

```bash
# 1. 全量导出（只读）
curl -s "http://127.0.0.1:8090/export?page_size=500&include_payload=true" > nodes.json

# 2. 用 core.confidence 算分
python -c "
from core.confidence import confidence_of, normalized
import json
for n in json.load(open('nodes.json'))['memories']:
    print(n['id'], confidence_of(n['payload'])['b'])
"

# 3. 打开 ε 后对比检索排序
MEMORY_CONFIDENCE_EPS=0.05 python scripts/palimpsest_cli.py search "你的查询"
```

## 六、已知局限

| 局限 | 说明 |
|---|---|
| **样本量** | 56 题、只有 7 题受影响。结论方向可信，具体数值不要当基准 |
| **证据是粗糙代理** | 正则从正文提取，「实测」这类词有约 8% 误报；`tested` 权重已按审计结果固定为 0.7 |
| **未做校准** | `b = 0.8` 目前**不**意味着「80% 的情况是对的」。校准需要「置信度 vs 后来是否被推翻」的历史数据，本库尚无 |
| **查询侧未放行** | 低置信记忆在语义检索里仍会返回（只是排名靠后）。若要支持「查询本身表达不确定时放宽」，需要额外的查询侧判断 |
| **只对中文/英文正文调过** | 证据正则同时覆盖中英，但只在中文库上实测 |

## 七、配置

| 变量 | 默认 | 说明 |
|---|---|---|
| `MEMORY_CONFIDENCE_EPS` | `0` | 置信度修正项强度。**0 = 关闭**；实测最优 `0.05` |
| `MEMORY_CONFIDENCE_CENTER` | `0.27` | `b` 映射到 0 的中心点 |
| `MEMORY_CONFIDENCE_SPAN` | `0.15` | 映射跨度：`b ≥ center + span` 截断到 +1 |

**建议**：先设 `MEMORY_CONFIDENCE_EPS=0.05` 观察真实检索日志，再决定是否长期开启。它只改变「分数相近的候选」之间的顺序，不会改变明显相关的排序。
