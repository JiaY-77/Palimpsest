# 检索质量评测

> 本文说明 Palimpsest 的离线检索质量评测体系：**题集怎么造、指标怎么定义、结果怎么读**，以及如何复现。
>
> 评测数据来自真实运行库。为保护个人数据，**原始题集与逐题结果不入库**（`.gitignore` 排除 `eval/*.json` 与 `eval/report_*.md`）；本文公开的是**方法**与**汇总结论**。
>
> 代码与实验记录见 [`eval/`](../eval/)（评测脚本、指标纯函数、14 份实验文档）。

---

## 一、为什么要自建评测

检索这类改动（切片粒度、融合方式、重排权重）有个通病：**「感觉变好了」不是证据**。

- 改了参数后，主观上「搜得更准了」很常见，但它可能只是**记住了改完后的那几条查询**；
- 多路检索（语义 / 全文 / 图谱）之间的权重关系更难凭直觉判断——某一侧权重抬一点，另一侧就相对被压；
- 没有对照，就无法回答「这次改动到底改善了什么、代价是什么」。

因此需要一套**可重复、有对照、能归因**的离线评测。

## 二、评测体系设计

### 2.1 题集构造（防作弊是重点）

题集由**库内真实节点反推**生成，而不是人工编题：

| 要点 | 做法 | 为什么 |
|---|---|---|
| 反推查询 | 取真实节点，让模型生成「用户会怎么问才能问到这条」 | 保证每题都有确定的正解，且查询分布贴近真实使用 |
| **禁止抄原文** | 生成后校验与原文的公共连续子串，**严禁 ≥6 字** | 否则测的是「字面抄写」，不是「语义检索」——这是评测有效性的关键 |
| 两类交替 | 口语化改写 / 含术语实体 | 覆盖「模糊问」与「精确问」两种真实形态 |
| 负样本 | 约 20 条，询问库中**确实不存在**的主题 | 衡量「不该召回时会不会乱召回」 |
| 固定随机种子 | 抽样与生成可重现 | 换机器、换时间跑，题集不变 |

题集按**层**打标签（记忆 / 知识库 / 小说 / 其他），便于分层报告——不同层的数据形态差异很大，混在一起算平均会互相掩盖。

### 2.2 四种检索模式对照

同一题集跑四条路径，横向对照：

| 模式 | 说明 |
|---|---|
| `fts` | 纯全文检索 |
| `vec` | 纯语义向量检索（不启用图扩散） |
| `rrf` | 融合排序（语义排名 + 全文排名的 reciprocal rank 求和） |
| `cascade` | 级联（全文粗筛 → 语义精排） |

**对照的意义**：能回答「融合到底有没有用」「级联在什么场景下更优」，而不是只证明「我那套能跑」。

### 2.3 指标定义

| 指标 | 定义 |
|---|---|
| Recall@K | 前 K 个结果中命中正解集合的比例 |
| MRR@K | 第一个命中结果的倒数排名（无命中记 0） |
| nDCG@K | 归一化折损累积增益（正解 1.0，同文档的其他切片 0.5） |
| **doc_recall@K** | 知识库题专用：同一来源文件的**其他切片**也视为相关（二值口径） |
| **正负样本可分离度（AUC）** | `P(随机正样本分数 > 随机负样本分数)`；0.5 = 完全无法区分，1.0 = 完美可分 |

最后一项是本体系的特色：**大多数评测只算召回，不问「误召回」**。有了负样本与可分离度，才能同时看到「该找的找到没有」和「不该找的有没有乱找」。

### 2.4 只读自证

评测全程在**库副本**上运行（脚本启动时复制库与 sidecar 文件，并把环境变量指向副本），避免污染真实数据；同时对真实库文件**跑前跑后各算一次 SHA256 并写入报告**，一致才标记通过。

> 这一条不是形式主义：评测会触碰 `hit_count` 之类的写入路径，直接跑真库会改变运行数据。

## 三、结果

### 3.1 整体指标（自评口径，含口径说明）

最新一轮全量评测（138 题，`vec` 单模式）的主要指标：

| 指标 | 值 |
|---|---|
| Recall@1 / @3 / @5 / @10 | 0.170 / 0.237 / 0.246 / 0.263 |
| MRR@10 | 0.203 |
| nDCG@5 | 0.212 |

**这个数字不高，且需要连同口径一起读**：

1. **题集是严格反推**（禁止抄原文），查询表述与原文的词汇重叠被刻意压到最低；
2. **全库跨层竞争**：记忆节点、知识切片、小说设定在同一候选池里抢排名，而题集里各层混合；
3. 因此这套数字衡量的是「**在一个混合的真实库里，语义检索单独作战能到什么程度**」，**不是**在公开 benchmark 上的表现，也不适合与其它系统的自报数字横向比较。

引入分层与文档级口径后，图景会清楚很多（见 3.2）。

### 3.2 分层结果

同一轮评测按层拆分（Recall@5）：

| 层 | Recall@5 | 说明 |
|---|---|---|
| 知识库（kb） | 0.550 | 且**文档级** `doc_recall@5` = **0.815**——即 top-5 里命中同一来源文件的比例超过八成 |
| 记忆（hermes） | 0.132 | 长文本记忆节点与短查询的粒度错配是主因（见 3.3） |
| 小说设定 | 0.050 | 该层数据形态特殊（人物卡高度相似），语义区分度天然低 |
| 其他 | 0.050 | 样本量小 |

**怎么读**：知识库场景（文档问答类 RAG 的典型场景）表现明显更好——**文档级召回 0.815 是这个体系里最有实用意义的一个数**；而记忆层的低分，正是下一节那项修正的起点。

### 3.3 消融实验：一次结构性修正

记忆层得分偏低，最初怀疑是衰减参数没调好。但分层消融给出了另一个答案：

**诊断**：原排序公式是**乘性硬加权**——

```
final = cosine × importance × decay^(天数/30)
```

其中元数据因子的取值范围约 0.25–0.90（跨度 > 3 倍），而候选之间的余弦分差通常只有 0.05–0.15（跨度约 1.5 倍）。**元数据的权重跨度大于语义分本身的跨度** → 排序被重要度与新鲜度主导，语义相关性被淹没。

这是**尺度失配**的结构性问题，不是参数取值问题。

**修正**：改为 **ε 级加性软加权**——语义分是主线，元数据只做小幅 tie-break：

```
final = cosine + ε × [归一化重要度 + 归一化新鲜度]        # ε 默认 0.02
```

同时把已被取代的旧版本节点从候选池中排除（原先约 24% 的候选是这类节点，占着名额却不展示）。

**对照结果**（138 题按层分层，Recall@5；此表为离线消融口径）：

| 层 | 改动前 | 仅软加权 | 软加权 + 候选排除 |
|---|---|---|---|
| 记忆（hermes） | 0.263 | 0.579 | **0.684** |
| 知识库（kb） | 0.700 | 0.675 | 0.700 |
| 小说设定 | 0.900 | 1.000 | 1.000 |
| 其他 | 0.050 | 0.600 | 0.600 |

**结论**：记忆层 Recall@5 提升约 2.6 倍，其余各层不倒退。**"语义为主、元数据为辅"这条原则，是用数据定下来的，不是设计时拍脑袋定的。**

**另一项同样重要的结论**：分块重打分的分数校准路线，前后做了三轮共 15 个变体，全部增益都在「≤1 题」的量级。据此判定该路线已到边际、**主动停止**——避免在一个收益与噪声同阶的方向上继续投入。

## 四、已知局限

1. **自评口径，非公开基准**：题集由本库反推，不能与 LoCoMo 之类的公开基准直接比较。
2. **题集规模有限**（百量级）：单个变体的差异若只有 ±1 题，不足以作为方向性证据；报告中凡涉及此类差异均标注了。
3. **分层不均衡**：小说层与「其他」层样本量小，其分数仅供参考。
4. **单次快照**：结果依赖当时库内数据分布；换库需重跑。
5. **幻觉率未直接度量**：本体系用「正负样本可分离度」间接衡量误召回风险，但没有端到端评估生成阶段的事实性。

## 五、如何复现

```bash
# 0. 前提：已装好依赖、Ollama 拉取了本地向量模型
venv/Scripts/python.exe eval/gen_eval_set.py            # 生成题集（需 LLM API）
```

产物：`eval/results_<UTC 时间戳>.json`（逐题排名）与 `eval/report_<时间戳>.md`（对照报告，含库 SHA256 一致性检查）。两者含个人库内容，故不入库。

## 六、显著性与时间切分（held-out）协议

> 动机：点估计没有方差，召回率上「几个点的差异」无法与噪声区分；且调参用的题集若同时是报告用的题集，每个数字都带乐观偏置。本节给两件工具：**时间切分 held-out** 与**配对显著性检验**（脚本与单测均在 `eval/`）。

### 6.1 时间切分：tune 用旧题，报告用新题

题集条目本身没有时间戳，切分以**每题 gold 节点的 `created_at`**（库内节点元数据，epoch 秒）为代理字段：指向较旧节点的查询进调参集（tune），指向较新节点的进报告集（held-out）——这也贴近真实使用（新查询随时间到达）。

```bash
venv/Scripts/python.exe eval/split_eval_set.py --tune-fraction 0.8
```

产物（都在 `eval/` 下，`.gitignore` 排除）：

- `eval_set_tune.json` / `eval_set_heldout.json`：两个子题集，`run_eval.py --eval-set` 可直接吃；
- `split_manifest.json`：**切分点显式记录**——边界 `created_at`（ISO 时间）、两侧 qid 清单、未切分计数。**调参运行不得触碰 held-out 集**。

局限（如实记录）：

1. 代理字段是 gold 节点创建时间，不是真实查询到达时间（题集离线反推，没有后者）；
2. gold 节点已被删除、或节点无 `created_at` 的题两边都不进，计数记在 manifest 的 `unplaced` 里——用切分结果前先看这个数；
3. 多 gold 题取最早的 gold 时间（保守：更可能落入 tune 集）；
4. 题集是单次快照，重建题集后**必须重新切分**。

### 6.2 配对显著性检验（bootstrap）

同一批查询上比较两套配置：逐题配对打分，对「逐题差值的均值」做 **centered bootstrap 双侧检验**（默认 1000 次重采样，add-one 修正保证 p 不为 0），置信区间用 **percentile 法**。纯标准库实现，无新增依赖。

```bash
# 例：同一份评测结果里比较 vec 与 rrf 两个模式的 recall@5
venv/Scripts/python.exe eval/significance.py \
    --results-a eval/results_X.json --mode-a vec \
    --results-b eval/results_X.json --mode-b rrf \
    --metric recall@5 --split-manifest eval/split_manifest.json
```

报告对每个集合（all / tune / held_out）各输出一行：`n`（配对题数）、`mean(A)`、`mean(B)`、`diff = mean(A) − mean(B)`、diff 的置信区间、p 值（H0：均值差为 0；p < 0.05 标 `*`）。

**逐题分数落盘**：`eval/comparison_<时间戳>.json` 保存每题两个配置的分数与所属集合，任何对比都可复现。

### 6.3 报告纪律

- **每个数字必须标明来自哪个集合**（tune / held-out / 全集）：调参时在 tune 集上看数字，**结论只引用 held-out 集**上的 n / mean / CI / p；
- 子集不足 2 题时检验不定义（脚本输出 n/a，不崩溃）；
- 统计函数单测在 `tests/test_eval_significance.py`（全等分数 → p=1；系统性赢 → p 极小；单题边界不崩）。

## 七、新鲜度加权（freshness weighting）

> 动机：`mem_search` 主线排序只看语义相似度（外加 fusion），没有时效概念——被 `REVISED_BY` 链显式取代的事实走 `outdated` 过滤处理了，但**没被标注、内容也不冲突的陈旧记忆**仍可能压住更新的真话。新鲜度是缺失的排序信号。

### 7.1 机制

在 `_mem_search_impl` 的过滤之后、排序之前（与 `domain_bias` / `domain_boost` 同层）应用：

```
score += MEM_SEARCH_FRESHNESS_WEIGHT × decay(节点年龄)
```

- 衰减信号 `decay ∈ [0,1]`，由 `core/bitemporal.py` 的 `freshness_decay` 计算：事实类节点（memory/task/plan）优先用世界时间 `valid_at`（缺省 `created_at`），其余节点（kb_chunk / record 等）用 `created_at`；
- 衰减形式：`exp`（半衰期，默认）或 `linear`（归零天数），尺度由 `MEM_SEARCH_FRESHNESS_SCALE_DAYS`（默认 30 天）控制；
- **默认权重 0 = 完全跳过**，行为与未引入前逐位一致（有回归测试保证）；
- **`as_of` 历史视图下不生效**——双时间线回看按「当时为真」排序，与今天的记忆新鲜度无关（验收红线）；
- 与 `MEMORY_DECAY_FACTOR` 的关系：后者只作用于 soft 重排的 ε 级微调项（量级 ≤0.02，近乎 tie-break）；本机制是检索主线上的独立加性信号，两者正交。

### 7.2 数据优先纪律

**非零权重必须由数据定出，不许拍脑袋定常数**。评测工具链：

```bash
venv/Scripts/python.exe eval/gen_eval_set.py     # 重建题集（需 LLM API）
venv/Scripts/python.exe eval/split_eval_set.py   # 重切 tune / held-out
DB_PATH=<生产库路径> venv/Scripts/python.exe eval/freshness_sweep.py \
    --weights 0,0.05,0.1,0.2 --decays exp,linear --scales 7,30,90 \
    --split-manifest eval/split_manifest.json
```

`freshness_sweep.py` 在库副本上走真实检索入口（`_mem_search_impl`）扫 (weight × decay × scale) 组合，输出每组 recall@k / MRR@10 / nDCG@5，并对每个非零组对 w=0 基线做配对 bootstrap 检验（复用第六章协议：tune 集选型、held-out 集报告）。副本只读，结束打印 SHA256 自证。

### 7.3 实测记录（2026-10-28）

> 如实记录，包括失败的尝试。

- **旧题集 gold 过期发现**：对 2026-09-10 生成的旧题集（118 条正样本）跑 sweep，指标全为 0。归因：库在 9-10 之后经历过 rebuild，节点 id 全部重排——34/118 条的 gold id 在库中已不存在，其余的 gold id 指向了内容移位后的其他节点（例：`q001` 的 gold=118，其原内容「为什么本地部署？为什么选 0.6b」现位于节点 2899）。检索本身工作正常（正确内容可被召回，只是 id 对不上）。**结论：全 0 是题集失效，不是检索失效**——这也是 issue #174「先修评测尺子」的直接证据之一。
- 处置：用 `gen_eval_set.py` 基于现库重建题集（gold 自动取现势节点 id），再切分、再 sweep。
- **工具链实跑（2026-10-28，题集重建前的预跑）**：`freshness_sweep.py` 在库副本上跑通，118 条正样本 × 2 组合（`w0/exp/d30` 基线、`w0.1/exp/d30`），逐题结果落 `eval/.tmp/freshness_sweep_<ts>.json`。所有指标为 0、配对 bootstrap `p=1.0`，与上一条归因一致：**是题集失效，不是检索失效，也不是加权失效**（基线 w=0 同样为 0）。
- 因此**权重取值暂无法定**，按数据优先纪律保持默认 0（关闭）发布；待 issue #221 重建题集并切分 tune / held-out 后，再跑完整网格（`--weights 0,0.05,0.1,0.2 --decays exp,linear --scales 7,30,90`），由 tune 集选型、held-out 集报告，结果回填本节。

## 八、题集重建与新参考点（#221，2026-10-28）

> 重建后的题集（`eval/eval_set_v2.json`）取代旧题集作为**判卷依据**：旧题集的 gold
> 存的是裸节点 id，2026-09-10 库 rebuild 后 id 全部重排，已无法判卷（见 8.1）。
> 但它目前只够作**方向性参考**——切分规模（tune 14 / held-out 4）远低于显著性检验
> 下限，原因如实写在 8.5；旧题集时代的数字保留作历史对照。

### 8.1 为什么旧题集作废

- 旧题集 138 题（semantic 72 / entity 46 / negative 20）的 `gold_ids` 是裸节点 id；
- 实测：118 条正样本里，gold id 仍在库的 84 条；其中过 split 口径（id 在库且
  `created_at` 非 None）的 54 条——但在**内容级验证**（query 与该节点 content 的余弦
  必须是该题 top1 且领先 runner-up ≥0.06）下，**没有一条原 gold 同时满足这两个条件**：
  id 重排后「id 存活、内容已换」是常态（例：q001 的 gold=118 现为一段压测反思，
  与其原内容「为什么本地部署/为什么选 0.6b」无关，后者现在位于节点 2899）；
- 这是**严格口径**，不等于「每条原 gold 都离谱」：个别原 gold 与题面仍有弱相关
  （q001 即一例，118 讲的仍是压测反思），只是达不到「可判卷」的无歧义标准。
  旧题集的根本问题是**判卷不可靠**，不是每条都错得彻底；
- 结论：旧题集跑出的任何数字都不构成证据，这正是「先修尺子」（#174）的原因。

### 8.2 重建方法（`eval/reresolve_gold.py`）

- 判定口径与 `split_eval_set.py` 一致（id 在库 + `created_at` 非 None = id 级
  存活），并在此之上做**内容级验证**；
- 对每条正样本，在**库副本**上按题集声明的 `gold_type` 取候选池（domain 只做
  窄池优先、不做硬过滤——题集 domain 标签与节点实际 domain 失配实测 35%+）；
- 用库内同款 embedding（Qwen3-Embedding，`iter_nodes` 读存量向量，query 侧
  `embed_text`）对 query 与候选 content 算余弦；
- 只在无歧义时改判：`top1 ≥ 0.60 且 top1 − runner-up ≥ 0.06`（runner-up 含原
  gold——改判必须赢过旧答案）。阈值取自全量打分分布的中位上沿（top1 p50=0.620、
  margin p75=0.068，分布表见 `eval/reresolve_report_*.md`），不是拍脑袋定值；

### 8.5 时间切分现状（tune 14 / held-out 4；目标未达成，原因如实说）

- 规模目标 tune ≥ 60 / held-out ≥ 30 **未达成**。根因两条：
  1. 可救条目上限：118 条正样本里仅 27 条改判到无歧义 gold（人工复核后再减 1 条）；
  2. **上游缺口**：kb_chunk（938 个）/ novel_chunk（124 个）/ git_commit（23 个）
     节点的 `payload.created_at` 全为 None——core 写入路径没写时间戳。改判落点
     在这三类节点的 10 条题因此进不了切分（27 条救回 → 18 条 placed → 14 + 4）。
- 治本要在 `core/` 的写入路径补 `created_at`（本任务禁改 core/，另行开 issue）；
  在那之前切分子集只够做方向性参考，不足以做显著性检验。
- 切分可复现且防搬动：manifest 钉 **qid**（含 unplaced 名单）；
  `split_eval_set.py --pin-manifest <旧manifest>` 重跑时按 qid 冻结分配，新增
  带判卷 gold 的题只进 `unplaced.new_qids_not_in_manifest`，已有切分不会被新增
  题悄悄搬动（2026-10-29 Phase-1 落地实测：pin 复跑 tune 14 / held-out 4 与
  boundary 与首切完全一致；新增只进未放置池）。
- **未放置池只增不减（2026-10-29 修复）**：pinned manifest 现携带
  `unplaced_qids` 逐条名单（negative_or_no_gold / missing_timestamp /
  new_qids_not_in_manifest）。此前 pin 链不回传未放置名单，会把旧的未放置
  批次反复当成「新增」上报（实测：连续 pin 第二轮把 110 条旧 qid 重报了一遍）；
 名单持久携带后复跑无变化即无新增。当前未放置池 13 条 = 9 条老题（改判落点在
  kb_chunk/novel_chunk/git_commit——created_at 缺失的三类节点）+ 4 条 Phase-1
  live（q140–q143，时间戳齐全，等主人显式重切决定归属）。旧格式 manifest 无名单
  时首轮会把未放置项报成新增一次，第二轮起名单固化。
- `pinned_resplit` 已抽成纯函数并有单元测试（tests/test_eval_report_determinism.py

## 九、小结

| 设计决策 | 依据 |
|---|---|
| 自建评测而非凭感觉 | 「感觉变好」无法排除记忆偏差 |
| 题集禁止抄原文 | 保证测的是语义检索，不是字面匹配 |
| 加入负样本与可分离度 | 同时衡量漏召回与误召回 |
| 分层报告 | 不同层数据形态差异大，混算会互相掩盖 |
| 语义为主、元数据为辅（ε 级加性） | 消融实验：原乘性加权存在尺度失配，修正后记忆层 R@5 0.263 → 0.684 |
| 评测在库副本上跑 + SHA256 自证 | 评测会触发写入路径，不能碰真实数据 |
| 显著性检验 + 时间切分 held-out | 点估计无法区分真提升与噪声；在调参集上自评必然乐观 |
| 题集每条带显式状态（live/reresolved/quarantined/dropped） | 库 rebuild 后裸 id 全失效，静默留坏 gold 比没有 gold 更糟（#221） |
| 新鲜度权重默认 0，非零取值须 sweep 数据背书 | 时效信号有价值，但常数必须来自真实查询集（issue #175） |

*本页只公开方法与汇总结论；原始题集、逐题结果与含个人数据的报告保留在本地。*
