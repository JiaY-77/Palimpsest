# Gate 0 报告：实体锚定层的图谱覆盖审计（PR0）

> 日期：2026-10-11 · 库：`data/mh_memory.db`（v2.7.0 生产库，1526 节点）
> 脚本：`scripts/entity_gate0.py`（只读，不动产品代码与数据）
> 目的：先证伪——**图里到底有没有「实体锚定 + 1~2 跳扩散」能吃到的增量？**

---

## 一、结论（先行）

**⛔ 停止 M1。图太稀疏，实体锚定吃不到增量。应先做「写边」（M2）。**

这不是"识别不准"的问题，是**图上根本没有路径**的问题——即便给完美的实体识别与锚点定位，1–2 跳也召回不到金标。

## 二、硬数据

### 2.1 图的规模（核心证据）

| 指标 | 数值 |
|---|---|
| 节点总数 | 1526 |
| **孤立节点（度=0）** | **1345（88.2%）** |
| 有边的节点 | 181（11.9%） |
| 出边总数 | 230 |
| **连通分量数** | **1393** |
| **最大连通分量** | **仅 26 个节点** |

图碎成 1393 块，最大一块 26 节点——**没有可扩散的结构**。

### 2.2 金标可达性（决定性的）

**评测集 `eval/manual_set.json`（15 条）：**

| 指标 | 值 |
|---|---|
| trigger_rate（识别出 ≥1 锚点） | 86.7% |
| reach@2（金标落在锚点 2 跳内） | **0.0%** |
| novel_reach@2（真实增量） | **0.0%** |
| 金标节点中孤立点 | **14 / 15** |

**全量集 `eval/eval_set.json`（138 条）：**

| 指标 | 值 |
|---|---|
| trigger_rate | 88.4% |
| reach@2 | **0.7%**（仅 1 条命中） |
| novel_reach@2 | **0.7%** |

### 2.3 上帝视角复核（排除"识别不准"的干扰）

直接从**金标节点本身**出发做 2 跳 BFS（假设锚点 100% 命中金标）——**15 个金标里 14 个 2 跳域 = 0**。也就是说：

> 就算锚点识别是完美的，实体路也一个金标都召不回——它们的图上没有任何邻居。

这排除了"是不是你 anchor 找错了"的反驳：**结论与识别质量无关**。

## 三、判定对照（规划 §7.2 的 kill criteria）

| 阈值 | 实测 | 判定 |
|---|---|---|
| `novel_reach@2 < 5%` → 停 | 0.0% ~ 0.7% | ⛔ **触发** |
| `reach@2 < 15%` → 停 | 0.0% ~ 0.7% | ⛔ **触发** |
| `trigger_rate < 30%` → 加 embedding 兜底 | 86.7% ~ 88.4% | ✅ 识别没问题 |

**注意**：`trigger_rate` 高达 88%，说明「查询里认得出实体」这件事**是可行的**——失败的**不是识别环节，是图本身**。这条信息对 M2 很重要：M2 写边之后，M1 的识别层可以原样复用。

## 四、对路线的影响

1. **M1（纯读侧实体锚定检索）搁置** —— 不是设计错，是**前置条件不满足**：图里没有边可扩散。
2. **应当先做 M2（写边）** —— 把记忆/知识库之间的关系写进图（对齐网页 AI 的判断：知识库关系查询本质是「现有图的边质量」问题）。
3. M1 的设计（Gate 0 脚本、EntityIndex 原型、RRF 第三路方案）**全部可复用**：等 M2 把图密度做上来，直接复跑本脚本即可重新判定。
