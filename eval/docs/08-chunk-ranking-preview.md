# 方向⑤预演：检索期分块重打分（否证）

## 问题

第 3 轮定位到 hermes / other 层检索差的根因之一是「**长且多主题的记忆节点 vs 短查询**」的
粒度错配，并提出方向⑤ small-to-big（长节点分块）。旧排序下一次测量显示分块可 +10.5pp，
但那次测量在语义主序被污染的前提下做的，需要在新排序下重测。

## 方法（不改索引的廉价近似）

正式的 small-to-big 要改索引 + 全库重嵌（高成本）。本脚本先验证它的**检索期近似**：
候选节点（干净语义序取 30 个）按内容切块（`chunk=400` 字、`overlap=100`），每块与查询
算余弦，取**最大块余弦**作为该节点分数，再重排取 top-10；与「整条内容余弦」对照。

同一库副本、同一题集（118 正样本）、`apply_decay=False`（纯余弦，排除 ε 干扰）。

## 结果

| 指标 | baseline（整条余弦） | chunk-max（分块取 max） | Δ |
|---|---|---|---|
| recall@1 | 0.4831 | 0.4576 | −2.5pp |
| recall@3 | 0.6780 | 0.6525 | −2.6pp |
| recall@5 | **0.7542** | 0.7288 | **−2.5pp** |
| recall@10 | 0.8136 | 0.7881 | −2.6pp |
| mrr@10 | 0.5882 | 0.5674 | −2.1pp |

分层 R@5：hermes 0.711 → **0.737**（+2.6pp），kb 0.750 → **0.650**（−10pp），
novel 1.000 → 1.000，other 0.600 → 0.600。

规模：118 题 × 30 候选 → 6184 块，耗时 339s（批量嵌入）。

## 结论

1. **检索期 chunk-max 在干净排序下是负收益（−2.5pp），否证「分块必涨」的预期**
   （旧排序下的 +10.5pp 包含排序污染的贡献）。
2. 失效机制清楚：**块数随节点长度增长，"取 max" 让长节点系统性占优**，破坏了跨节点的
   分数可比性——hermes 层因此小涨（+2.6pp），代价是 kb 层被挤掉（−10pp）。
   即使实现里做了 `max(整条, 块最大)` 兜底，长节点偏置仍然存在。
3. 要真正吃到分块收益，必须解决可比性，可选路径：
   - 长度归一化（如 block 分取 top-2 平均、或除以 √块数）
   - 只对记忆类长节点分块（分层策略），知识块保持整条
   - 索引期 small-to-big（块级召回、节点级返回）——成本最高但最干净
4. **因此方向⑤不能按「直接上分块」推进**；下一步应先做「长度归一化 + 分层分块」的
   离线小实验，确认能把 hermes 的 +2.6pp 拿到手且不伤 kb，再谈动索引。

## 已知边界

- 分块粒度只试了 `400/100` 一档；更粗（800/200）或按 Markdown 标题切可能不同。
- 本次只做「重排」不改索引，块向量是查询时现算的（离线跑不敏感，生产要算延迟：
  6184 块 / 118 题 ≈ 52 块/查询，批量嵌入约 1s 量级）。
